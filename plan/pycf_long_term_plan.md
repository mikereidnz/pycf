# Long Term Plan for the Development of pycf

## 1. Purpose and Scope

This document defines a practical plan for developing the pycf repository, covering:

- Correctness and scientific reliability
- Build and packaging health
- Test quality and coverage
- Performance and memory behavior
- API usability and documentation quality
- Maintainability and technical debt

## 2. Audit Goals

- Validate that core numerical workflows produce stable and reproducible results.
- Confirm the C core and Python bindings build cleanly in supported environments.
- Identify high-risk bugs, regression risks, and untested behavior.
- Review code quality hot spots in both C and Python layers.
- Produce prioritized remediation actions with owners and timelines.

## 3. Repository Areas to Review

### 3.1 Core Native Layer (`cfl/`)

- `cfl/src/` and `cfl/include/` for algorithm correctness, memory safety, and error paths.
- Build flags and platform assumptions in `cfl/makefile`.
- Native tests under `cfl/tests/` and execution wrapper `cfl/cfl_testing.sh`.

### 3.2 Python/Cython Interface (`pycf/cfl.pyx`, `setup.py`, `pyproject.toml`)

- Object lifetime, ownership, and capsule cleanup paths.
- NumPy array assumptions (contiguity, dtype, shape, alignment).
- Build integration (PEP 517 via `pyproject.toml` with setuptools backend; `setup.py` still drives the Cython extension and `cfl/libcfl.a` build), extension linking, and version generation behavior.

### 3.3 Pure Python Modules (`pycf/*.py`)

- Parsing and ingestion logic (`import_sljm.py`).
- Utility and reporting logic (`cfl_util.py`).
- Spin-Hamiltonian and EMP wrappers (`spinh.py`, `pyemp.py`).
- Calculation of crystal field and intensity parameters (`paramcalc.py`)
- Calculation of intensities (`inten.py`)
- Matrix-element generation to replace the legacy Pascal code is tracked
  as a follow-up task (see §8.6).

### 3.4 Tests, Docs, and Examples

- Unit/integration tests under `tests/`.
- User documentation under `docs/`.
- End-to-end sample workflows in `examples/`.

## 4. Audit Checklist

### 4.1 Build and Environment

- Verify `python setup.py build_ext --inplace` succeeds from clean state.
- Verify `make -C cfl` and `make -C cfl test` succeed.
- Validate optional environment-path settings (`CFL_CFLAGS`, `CFL_LDLIBS`, `CFL_CC`, `INTEL_PATH`).

### 4.2 Correctness and Reliability

- Cross-check representative numerical outputs against known baselines. This has been done in some cases:
    - `tests/integration/spin-half/test_spin-half.py` compares the pycf eigenvectors to eigenvectors generated by `numpy.linalg.eig`.
    - `tests/inten/` contains scripts that compare dipole strengths, oscillator strengths, and Einstein A coefficients to calculations by Pascal code (`linuxemp`).
    - `tests/integration/eryso/` and `tests/integration/ceylf/` contain tests that fit data and check the resulting parameters against results from legacy pycf calculations.
    - `tests/unit/` contains targeted unit tests for the Hamiltonian-data accessors, importer, label parsing, and similar Python-side helpers.
These examples need to be extended and better documented, for example with printouts from other software.
- Review handling of edge cases (empty inputs, malformed labels, non-Hermitian input).
- Confirm deterministic behavior where expected (or document stochastic sections).

### 4.3 Safety and Error Handling

- Inspect error propagation from C to Cython to Python exceptions.
- Check for potential memory leaks, double-free paths, and unchecked allocations.
- Verify file/IO parsing failures return actionable errors.

### 4.4 Test Health

- Run pytest suite and classify failures by severity and component.
- Assess coverage blind spots and add targeted tests for high-risk branches.
- Ensure example workflows are exercised and results are sanity-checked.

### 4.5 Performance

- Benchmark representative workloads against current baseline.
- Profile hotspots in C routines and high-level Python orchestration.
- Note regressions and potential optimizations with expected impact.

### 4.6 API and Documentation

- Review public API consistency, naming, and deprecation behavior.
- Validate docs and quickstart instructions against actual commands.
- Confirm examples reflect current API contracts.
- Differences between this version and the legacy version are recorded
  in `CHANGELOG.md` (notable items: the LAPACK conjugation fix, MAGX/MAGY
  sign correction, `inten.py` electric-dipole correction, `gsl_nls`
  weight overcounting fix, C memory-management fixes, percentage display
  fix, and the `dry_run` / Hamiltonian-data accessor extensions).  See
  also §8.1/8.2 for the Python-side residual builder and minimizer
  follow-ups, and §8.5 for the multi-user installation flow.

## 5. Execution Phases

### Phase 1: Baseline and Inventory

- Gather current build/test status and existing known issues.
- Map critical modules and data-flow boundaries.

### Phase 2: Deep Technical Review

- Perform targeted code review by component.
- Record defects, risks, and confidence levels.

### Phase 3: Validation and Reproduction

- Reproduce findings with minimal scripts/tests.
- Confirm severity and user impact.

### Phase 4: Reporting and Action Plan

- Produce prioritized findings list.
- Propose fixes, effort estimates, and rollout order.

## 6. Deliverables

- Audit findings report (severity-ranked).
- Risk register with mitigation recommendations.
- Test-gap report and proposed new tests.
- Build and environment compatibility notes.
- Follow-up implementation plan.

## 7. Exit Criteria

- All critical/high findings have an approved remediation path.
- Reproducible build/test instructions are verified.
- High-risk code paths are covered by automated tests.
- Documentation reflects current behavior and known limitations.

## 8. Follow-up Tasks

### 8.1 Extend Hamiltonian data accessors to remaining fit classes and modes

The accessors added in `plan/hamiltonian_data_plan.md` (`get_edata`,
`fd_jacobian`, `covariance`, `last_jacobian`) currently support only `EFit`
and `MHFit`, and only for absolute/difference observation modes (`'A'`,
`'D'`).  Outstanding gaps:

- **State-label modes (`'AS'`/`'DS'`, a.k.a. `sl_diff`).**  Implemented
  for `EFit` and `MHFit` (commit replacing the `NotImplementedError`
  guards): `_build_edata_for_ex` now matches each observation's state
  label against the principal component of every eigenvector via
  `ex_parse_abs`/`ex_parse_diff`, mirroring `find_sort_indices` in
  `cfl/src/cfl_h_fit.c`.  `kind` becomes `'AS'`/`'DS'` and the dtype
  has been widened to `U2`.  Note that the matched index can shift
  under finite-difference perturbation; if a swap occurs at a
  parameter `x ± δ`, `fd_jacobian` reports it via the existing
  `check_swaps` machinery.  `ESHFit`/`MESHFit` still need the same
  treatment.

- **`ESHFit` (single Hamiltonian + spin-Hamiltonian, `cfl.esh_fit`).**  Used
  by `examples/ceylf/shfit_example.py`.  Has its own residual block for the
  spin-Hamiltonian terms; the energy block could be exposed by an
  `EData`-equivalent accessor, but the Jacobian/covariance helpers would
  need to choose whether to include the spin-Hamiltonian residuals or
  restrict to the energy block.

- **`MESHFit` (multi-Hamiltonian + spin-Hamiltonian, `cfl.mesh_fit`).**
  Used by `examples/eryso/mesh_fit*.py` and `examples/eryso/mhfit_siman.py`
  (the latter via `mh_fit`, which *is* covered).  Per-Hamiltonian weights
  are stored as dicts (`weights_list[i]['energy']`, plus spin-Hamiltonian
  keys), so `_build_edata_for_ex` would need a small adapter to pick the
  energy weight and a decision (as for `ESHFit`) about whether the
  Jacobian/covariance should span the spin-Hamiltonian residuals too.

Suggested rollout order: `MESHFit` energy-block accessors first (used by
the eryso examples), then `ESHFit`, then state-label modes across all four
fit classes.

### 8.2 Python-side residual builders, irrep assignment, and minimizers

Implementing state-label (`'AS'`/`'DS'`) support for `get_edata` /
`fd_jacobian` (see §8.1) effectively requires reproducing in Python the
state-matching step that the C residual builder performs.  Once that
Python residual builder exists, several adjacent extensions become
inexpensive:

- **Irrep-based assignment.**  A natural generalisation of state-label
  matching: instead of (or in addition to) matching by SLJM-style labels,
  classify each computed eigenvector by its irreducible representation
  under the site point group and match observations tagged with an irrep
  label.  This is most useful for high-symmetry cases (cubic, hexagonal,
  tetragonal) where irreps are well-defined and the experimental
  assignments are typically given that way.  The extension needs:
  - A character-table / projection-operator helper (likely a small new
    Python module).
  - A way to specify the site group on the `Hamiltonian` (or on the
    `ExData`).
  - An ``ExData`` mode like `'AI'`/`'DI'` (or a generalised label-key
    scheme) so observations carry an irrep label.

  This step requires physics input (which groups, which conventions,
  which character tables) before implementation.

- **Python-side minimizers.**  Once residuals and Jacobians are built in
  Python (via `get_edata` / `fd_jacobian` / `last_jacobian`), wrapping a
  pure-Python minimizer is straightforward — `scipy.optimize.least_squares`
  (Levenberg-Marquardt or Trust-Region-Reflective), `lmfit`, or a
  hand-rolled Gauss-Newton step are all viable.  This is much cheaper to
  develop and maintain than extending the C `cfl_min` infrastructure, and
  is an excellent fit for high-symmetry problems where each Hamiltonian
  diagonalisation is cheap (small block-diagonal matrices) so the Python
  overhead per iteration is negligible relative to `cfl/`'s dense LAPACK
  call.  Low-symmetry cases like eryso would still benefit from staying
  on the C minimizers.

  Suggested ordering: ship a thin `scipy_least_squares` wrapper that takes
  an `EFit` / `MHFit` instance and uses `get_edata` + `fd_jacobian` (or an
  analytic Jacobian once available) as its callbacks; that wrapper then
  becomes the natural integration point for irrep-aware residuals.

  **Status:** the wrapper now exists as `pycf.pyfit.PyFit` (see
  `examples/ceylf/pyfit_example.py`).  It uses `_temporary_x` +
  `get_edata` to feed weighted residuals to `scipy.optimize.least_squares`
  and supports any scipy method, bounds, and custom Jacobians.  Note that
  the C-minimizer path now integrates consolidated Cython objectives for
  mu/n marker-column fitting (see §8.2a), so PyFit's pure-Python approach
  is most valuable when Python control or scipy methods are explicitly
  needed.  Remaining work in this section: irrep assignment, analytic
  Jacobians, and any `lmfit` / Gauss-Newton variants.

These items are speculative until the §8.1 state-label work is
underway — listed here so they are not lost.

### 8.2a Marker-column dynamic mu/n fitting optimization (COMPLETED)

The marker-column mu/n fitting path (`'MuN'` label key) experienced a critical
performance regression (23–30× slowdown vs. baseline) due to excessive C↔Python
boundary crossing in the objective function callback (5+ crossings per iteration
× 100+ iterations).

**Solution implemented (commits f910e55, abf563f, 5543250):**

- **Consolidated Cython objectives:** Replaced multiple Python wrappers with
  dedicated Cython functions (`mu_n_efit_obj`, `mu_n_mhfit_obj`) that perform
  all mu/n mapping and chi² computation in a single Python context (one
  boundary crossing per objective call instead of 5+).
  
- **Shared chi² helper:** Created `compute_chi2_numpy()` in `cfl_util.py` to
  compute weighted sum of squared residuals using vectorized NumPy.  Used by
  both the consolidated fitting objectives and display functions, ensuring
  fit and display use the same source of truth.
  
- **Performance results:**
  - Single EFit: 283× speedup (6 sec → 0.02 sec)
  - 13-Hamiltonian MHFit: 5.5 sec (2.75× overhead acceptable for dynamic mapping)
  - Irreducible overhead due to level reordering during optimization
  
- **Test coverage (22 new tests):**
  - 12 unit tests for `compute_chi2_numpy()` covering weighted residuals,
    invalid indices, edge cases, and consistency with C echisq formula
  - 10 integration tests for marker-column formats: pure 'mu', pure 'lev',
    mixed formats; absolute and difference energy modes

**Outstanding items:**

- Add physically realistic MHFit integration tests with multi-Hamiltonian
  scenarios (multiple field orientations, hyperfine coupling, etc.) that
  exercise level reordering and verify parameter convergence against
  expected physics.  These should be added by a user familiar with the
  specific material systems being studied.
  
- Extend edge-case coverage: test fits where eigenstate ordering changes
  significantly during minimization, fits with multiple distinct mu values,
  and performance characterization across system sizes.
  
- Document best practices: when to use mu/n vs. static level indices,
  performance expectations for different Hamiltonian sizes, and mu/n
  fitting diagnostics.

### 8.3 `ImportTensors` round-trip and non-Hermitian handling

The `import-tensors-non-hermitian` work (now merged into `devel`)
established the policy that pycf only supports Hermitian operators:
`ImportTensors` round-trips raw tensor data through the importer, and
non-Hermitian inputs are explicitly rejected.  The companion
`zhcsr2zha` correction in the C layer fixed a subtle CSR→dense conversion
bug.  Outstanding items:

- Add a regression-style integration test that reads, writes, and
  re-reads a representative tensor file and asserts byte-for-byte
  equality of the persisted form.
- Decide whether to expose a small public helper for "is this tensor
  Hermitian within tolerance?" so user-supplied tensors can be checked
  consistently across `import_sljm.py`, `cfl.pyx`, and any future
  matrix-element generator (§8.6).
- Document the Hermitian-only policy and the recommended way to
  introduce non-Hermitian operators (e.g. via paired Hermitian and
  anti-Hermitian components).

### 8.4 CI / sanitizer infrastructure

The current GitHub Actions workflow runs the test suite on Python
3.10–3.13 and includes AddressSanitizer + UndefinedBehaviorSanitizer
builds; wheels are produced via `cibuildwheel` against
`manylinux_2_34`.  Outstanding items:

- Extend the sanitizer matrix to exercise the new Hamiltonian-data
  accessors and any future Python-side residual builder (§8.1, §8.2)
  so memory issues introduced through the Cython boundary are caught
  early.
- Add a coverage gate for the `[test]` extra so dropping a dependency
  silently doesn't degrade CI.
- Periodically refresh the sanitizer toolchain pin and the
  `manylinux_2_34` image to track upstream security fixes.

### 8.5 Multi-user server installation

`INSTALL.md` now documents the recommended pattern for sharing a single
pycf checkout across multiple users on a server (each user creates
their own venv and `pip install -e <shared-pycf>[examples]`).
Outstanding items:

- Decide whether pycf should ship a small helper script (e.g.
  `scripts/pycf-create-user-venv`) that automates the per-user venv
  creation and activation-function snippet.
- Add a CI job (or a manual smoke-test recipe) that exercises the
  documented `pip install -e <shared>[examples]` flow against a clean
  venv to catch packaging regressions.
- Document permissions expectations (read-only access to the shared
  checkout; `pip install -e` only writes the `.egg-info` and built
  extension which the user owns).

### 8.6 Matrix-element generation (replace legacy Pascal `linuxemp`)

pycf currently relies on matrix-element data produced by the legacy
Pascal `linuxemp` toolchain.  A native generator inside pycf would
remove that dependency and unlock additional configurations.
Requirements:

- Cover the f^N configurations already supported and extend to d^N
  and mixed configurations such as f^(N-1)d.
- Include hyperfine interactions (the new generator must produce HYP
  tensors compatible with the existing `ImportSLJM` consumers).
- Integrate with `ImportSLJM` / `ImportTensors` so existing examples
  and tests continue to work without rewrites.

Implementation could draw on existing open-source angular-momentum
libraries (e.g. SymPy's recoupling / 6j/9j routines, or a dedicated
package) but the choice should be made deliberately: licensing,
numerical precision, and ability to express hyperfine matrix elements
are all relevant criteria.

### 8.7 Coverage and test-gap closures

The §4.4 target is 95%+ on critical modules.  Outstanding items:

- Track current coverage per module in CI artefacts and surface
  modules below the target.  `pyemp.py` is intentionally excluded as
  legacy; `paramcalc.py` and `inten.py` are the next candidates for
  focused test work.
- Add tests that exercise error paths (malformed input files, missing
  matrix-element directories, mismatched label keys) which are
  presently hard to trigger from the existing examples.

### 8.8 `inten.py` user-facing output and polarization options

`inten.py` currently prints raw arrays and dictionaries; for end users
this is hard to read and easy to misinterpret.  Planned work:

- Build a proper textual / tabular summary akin to `gen_e_summary`
  (column-aligned, with column headings, units, and selection-rule
  labels).  Consider returning a structured object (analogous to
  `EData`) so downstream code can format or filter without re-parsing.
- Expand polarization handling.  At minimum: linear σ / π for the
  conventional uniaxial case; circular polarization (σ+ / σ-) for
  magneto-optical and Zeeman work; isotropic / unpolarized averages.
  The polarization choice should be a first-class API parameter, not
  buried in keyword arguments.
- Add tests for each polarization option that compare against
  hand-computed analytic results for a small system (e.g. spin-1/2
  in a magnetic field) to lock the conventions down before extending
  to multi-electron cases.

This is the highest-priority item for the next development cycle.
