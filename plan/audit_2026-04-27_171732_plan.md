# Plan for Auditing the pycf Repo after the initial upgrade to v0.1.0

## 1. Purpose and Scope

This document defines a practical audit plan for the pycf repository, covering:

- Correctness and scientific reliability
- Build and packaging health
- Test quality and coverage
- Performance and memory behavior
- API usability and documentation quality
- Maintainability and technical debt

## 2. Audit Goals

- Validate that core numerical workflows produce stable and reproducible results.
- Confirm the C core and Python bindings build cleanly in supported environments.
- Identify high-risk bugs, regression risks, and untested behavior.
- Review code quality hot spots in both C and Python layers.
- Produce prioritized remediation actions with affected components, evidence, and suggested ordering.

## 3. Repository Areas to Review

### 3.1 Core Native Layer (`cfl/`)

- `cfl/src/` and `cfl/include/` for algorithm correctness, memory safety, and error paths.
- Build flags and platform assumptions in `cfl/makefile`.
- Native tests under `cfl/tests/` and execution wrapper `cfl/cfl_testing.sh`.

### 3.2 Python/Cython Interface (`pycf/cfl.pyx`, `setup.py`)

- Object lifetime, ownership, and capsule cleanup paths.
- NumPy array assumptions (contiguity, dtype, shape, alignment).
- Build integration, extension linking, and version generation behavior.

### 3.3 Pure Python Modules (`pycf/*.py`)

- Parsing and ingestion logic (`import_sljm.py`).
- Utility and reporting logic (`cfl_util.py`).
- Spin-Hamiltonian and EMP wrappers (`spinh.py`, `pyemp.py`).
- Calculation of crystal field and intensity parameters (`paramcalc.py`)
- Calculation of intensities (`inten.py`)

### 3.4 Tests, Docs, and Examples

- Unit/integration tests under `tests/`.
- User documentation under `docs/`.
- End-to-end sample workflows in `examples/`.

## 4. Audit Checklist

### 4.1 Build and Environment

- Verify `python setup.py build_ext --inplace` succeeds from clean state.
- Verify `make -C cfl` and `make -C cfl test` succeed.
- Validate optional environment-path settings (`CFL_CFLAGS`, `CFL_LDLIBS`, `CFL_CC`, `INTEL_PATH`).

### 4.2 Correctness and Reliability

- Cross-check representative numerical outputs against known baselines. This has been done in some cases:
    - The `tests/spin-half` directory contains a script (`test_spin-half.py`) that compares the pycf eigenvectors to eigenvectors generated by numpy.linalg.eig. 
    - The `tests/inten` directory contains scripts that compare dipole strengths, oscillator strengths, and Einstein A coefficients to calculations by pascal code (`linuxemp`). 
    - The `tests/eryso/` and `tests/ceylf` contain tests that fit data and test the resulting parameters against results from legacy pycf calculations. 
These examples need to be extended and better documented, for example with printouts from other software. 
- Review handling of edge cases (empty inputs, malformed labels, non-Hermitian input).
- Confirm deterministic behavior where expected (or document stochastic sections).

### 4.3 Safety and Error Handling

- Inspect error propagation from C to Cython to Python exceptions.
- Check for potential memory leaks, double-free paths, and unchecked allocations.
- Verify file/IO parsing failures return actionable errors.

### 4.4 Test Health

- Run pytest suite and classify failures by severity and component.
- Assess coverage blind spots and add targeted tests for high-risk branches.
- Ensure example workflows are exercised and results are sanity-checked.

### 4.5 Performance

- Benchmark representative workloads against current baseline.
- Profile hotspots in C routines and high-level Python orchestration.
- Note regressions and potential optimizations with expected impact.

### 4.6 API and Documentation

- Review public API consistency, naming, and deprecation behavior.
- Validate docs and quickstart instructions against actual commands.
- Confirm examples reflect current API contracts.
- Carefully document differences between this version and the legacy version. Differences  include the following:
    - Complex conjugating matrices before diagonalization to take into account the behaviour under the parameters used to call `LAPACKE_zheevr_work`. This change is validated in `test_spin-half.py`. This makes no difference to energy levels, but the change in internal eigenvector phases affects other calculations, such as intensities and projection of spin Hamiltonians. 
    - Bug fixes to the code in `inten.py`, which was incorrect for electric-dipole moments. This has little impact as the code was (and still is) incomplete. However, the current code correctly reproduces the legacy pascal calculations (`tests/inten`)
    - Some errors in overcounting of weights in `gsl_nls` were corrected. This will affect some fits with multiple Hamiltonians with different weights. 
    - An audit of the C code uncovered some memory-management issues. Most of them were harmless, such as not deallocating memory when allocation failed, which would have resulted in the run halting. However, some of the memory issues could affect results - the old version would have corrupted some memory.  
    - Corrected calculation of eigenvector percentages in `cfl_util.py`. Cosmetic fix. 
    - Minor change to return `fmin` in the case `dry_run=True`, so user can assess changes made by hand and potentially allow users to write alternative minimization routines in python, perhaps including intensity calculations. Alternative minimization routines would benefit from other extensions: Return experimental and calculated energies in an easily digested vector form; Optionally return derivatives of calculated energies with respect to Hamiltonian parameters. 
    

## 5. Unattended Execution Protocol

The audit should be runnable without interactive clarification. Use the following defaults unless a later user instruction explicitly overrides them.

### 5.1 Operating Rules

- Run commands from the repository root.
- Do not modify source files while auditing, except for generated build/test artifacts. If a finding requires a fix, document it rather than applying it.
- Do not ask follow-up questions during an audit run. Use this protocol's defaults, state any assumptions, and continue.
- Record the starting `git status --short` and do not revert or overwrite pre-existing user changes.
- If a prerequisite is missing, do not stop the audit. Mark the affected check as `blocked`, include the exact missing dependency or command failure, and continue with independent checks.
- If an external tool or dataset is optional or not present (for example EMP/linuxemp executables, Pascal reference tools, Intel/MKL paths, `bandit`, `semgrep`, `pre-commit`, or benchmark plugins), skip only that check and report it as `not run`.
- Do not install or upgrade packages during the audit unless the user explicitly asks. Report missing packages as environment issues.
- Prefer concise command output in the final report: summarize pass/fail status, include command lines, and quote only the relevant failure excerpts.

### 5.2 Baseline Commands

Run these first and include results in the report:

```bash
git --no-pager status --short
python --version
python -c "import numpy, scipy; print('numpy', numpy.__version__); print('scipy', scipy.__version__)"
gcc --version | head -1
```

### 5.3 Required Build and Test Checks

Run these checks in order. Continue after failures where later checks are independent.

```bash
make -C cfl clean
make -C cfl
make -C cfl test
python setup.py build_ext --inplace
python -c "import pycf; from pycf import cfl, inten; from pycf.import_sljm import ImportSLJM; print('imports ok')"
python -m pytest tests/ -q --cov=pycf --cov-report=term-missing
```

After the normal pytest suite, run slow tests separately and run benchmarks if `pytest-benchmark` is installed:

```bash
python -m pytest tests/ -q --runslow
python -m pytest tests/test_benchmarks.py -q --benchmark-only
```

### 5.4 Optional Static Analysis Checks

Run these only if the commands and configuration files are available:

```bash
mypy pycf/ --ignore-missing-imports --no-error-summary
python -m pylint pycf/*.py --disable=all --enable=E,F
flake8 pycf tests
bandit -c .bandit -r pycf/
semgrep --config=.semgrep.yml pycf/
pre-commit run --all-files
python -m sphinx -b html docs docs/_build/html
```

Treat static-analysis warnings as findings to triage, not as automatic audit failures. Prioritize errors that can affect scientific results, memory safety, packaging, or user-visible behavior.

### 5.5 Manual Review Targets

When reviewing code, focus on the highest-risk paths first:

- C memory ownership and allocation failure paths in `cfl/src/*.c` and public contracts in `cfl/include/*.h`.
- Cython object lifetime, `PyCapsule` cleanup, exception translation, and NumPy shape/dtype/contiguity checks in `pycf/cfl.pyx`.
- Matrix-element parsing, label canonicalization, tensor synthesis, and malformed-file errors in `pycf/import_sljm.py`.
- Numerical correctness and legacy-behavior deltas in `pycf/inten.py`, `pycf/spinh.py`, `pycf/paramcalc.py`, and `pycf/cfl_util.py`.
- Packaging and CI consistency across `pyproject.toml`, `setup.py`, `INSTALL.md`, and `.github/workflows/*.yml`.

**Legacy modules.**  Files whose module-level docstring begins with the
token `LEGACY:` (see CONTRIBUTING.md "Legacy modules") are out of scope
for detailed review.  Only `critical`-severity findings (command
injection, memory corruption, exploitable security issue, or
import-time crash) are reported and fixed in those modules; lint,
typing, coverage, dead-code, and stylistic findings are intentionally
suppressed.  When walking through the source tree, skip `LEGACY:`-marked
modules after a quick scan for security-critical patterns.

### 5.6 Severity and Confidence

Classify every finding with both severity and confidence:

- `critical`: likely wrong scientific results for common workflows, memory corruption, exploitable security issue, or total inability to build/install.
- `high`: incorrect results or crashes in important but narrower workflows, serious resource leak, broken supported-platform behavior, or missing tests around recently changed numerical behavior.
- `medium`: edge-case bug, confusing API behavior, fragile packaging, incomplete error handling, or meaningful documentation/test gap.
- `low`: cosmetic issue, minor documentation drift, non-blocking maintainability concern, or optional-tool warning.

Use confidence values `confirmed`, `likely`, or `speculative`. A `confirmed` finding needs a command, test, traceback, sanitizer output, or file/line evidence. Mark speculative concerns clearly and do not present them as defects.

### 5.7 Report Format

Report back in this structure:

1. Executive summary: overall health, highest-risk issue, and whether the repo is ready for release/use.
2. Environment and baseline: Python/compiler/dependency versions and starting git status.
3. Command results table: command, result (`passed`, `failed`, `blocked`, `not run`), and key evidence.
4. Findings table: ID, severity, confidence, component, evidence, impact, reproduction steps, and recommended remediation.
5. Test and documentation gaps: missing coverage, missing baselines, and docs that disagree with observed behavior.
6. Suggested remediation order: what to fix first and why, without assigning people or estimating dates.
7. Appendix: longer logs or stack traces only where needed to support findings.

## 6. Execution Phases

### Phase 1: Baseline and Inventory

- Gather current build/test status and existing known issues.
- Map critical modules and data-flow boundaries.

### Phase 2: Deep Technical Review

- Perform targeted code review by component.
- Record defects, risks, and confidence levels.

### Phase 3: Validation and Reproduction

- Reproduce findings with minimal scripts/tests.
- Confirm severity and user impact.

### Phase 4: Reporting and Action Plan

- Produce prioritized findings list.
- Propose fixes, likely scope, and rollout order.

## 7. Deliverables

- Audit findings report (severity-ranked).
- Risk register with mitigation recommendations.
- Test-gap report and proposed new tests.
- Build and environment compatibility notes.
- Follow-up implementation plan.

## 8. Exit Criteria

- All critical/high findings have an approved remediation path.
- Reproducible build/test instructions are verified.
- High-risk code paths are covered by automated tests.
- Documentation reflects current behavior and known limitations.

## 9. Suggested Execution Order

- Baseline, inventory, and build/test verification.
- Core C and Cython interface audit.
- Python modules, docs, and example workflow audit.
- Consolidated report, remediation prioritization, and handoff.
