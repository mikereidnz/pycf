## Deep-check findings — `pycf`

### C core (`cfl/src`) — most serious issues

**🔴 Critical — data race in parallel ZEFOZ search.** `zefoz_search` runs `#pragma omp parallel for` (`cfl_zefoz.c:542`). Every per-thread `zd_inst` stores the **same** Hamiltonian pointer (`data->h = h`, `cfl_zefoz.c:235`). Inside the loop, `zefoz_iter` writes `data->h->coeff[...]` (`:434`) while `zhd`→`zhcsrsama` reads the whole `h->coeff` array (`cfl_h.c:976`). Concurrent unsynchronized read/write of shared `coeff` → silently wrong eigenvalues/gradients in the default multi-threaded path. The struct comment (`:155-158`) even warns about exactly this. Only `zefoz_a_insert` is under `critical`.

**🟠 High — out-of-bounds thread indexing.** `ninst = omp_get_num_procs()` (`cfl_zefoz.c:265`) sizes `d_inst[]`, but the parallel region has no `num_threads` clause. If `OMP_NUM_THREADS > num_procs`, `tn = omp_get_thread_num()` indexes past `d_inst` → wild pointer deref. Contrast `cfl_h.c:304` which correctly pins `num_threads(ndiag_w)`.

**🟠 High (verify vs. PRB 74,195101) — ZEFOZ Newton step ~4× too large.** `d2()` (`cfl_zefoz.c:343`) computes `Σ Re(⟨k|Mᵢ|l⟩⟨l|Mⱼ|k⟩)/(Eₖ−Eₗ)`, which is **half** the true Hessian (the two operator orderings have equal real parts since M is Hermitian — I verified this). So the Jacobian `J = 2·C`, and Newton should be `ΔB = −0.5·C⁻¹v`. The code does `B -= 2*dwork` i.e. `−2·C⁻¹v` (`:462`), a factor-4 overshoot that can destabilize convergence. Worth checking against the reference and `zefoz_test` tolerance.

**🟡 Low — FD gradient base point not restored.** `gsl_numerical_df_wrapper` (`cfl_min.c:177`) leaves `df_work[i]` at the last probe value, so later coordinates are differentiated at a point offset by ~1e-9. Tiny error, but a genuine deviation.

**🟡 Low — comment imprecision.** `svd_sym` (`cfl_sh.c:664`) computes the nearest symmetric *PSD* matrix (`V S Vᵀ`), not "nearest symmetric matrix" (`(A+Aᵀ)/2`).

Allocation/free ordering, the block-diagonal solver threading, `zhcsrsama` accumulation, and the chi-squared reductions were checked and are correct.

Subject: three issues in ZEFOZ search (concurrency + Newton step) — findings & suggested fixes

Hi Sebastian (or ZEFOZ maintainer),

I ran a deep code review and found three actionable issues in the ZEFOZ routines that can produce incorrect results or crashes when running multi-threaded. I did not change ZEFOZ code; below are precise citations, why each is a problem, and suggested fixes + test suggestions. I can open a PR with any of these fixes if you prefer.

1) Critical — concurrent writes to shared h->coeff (data race)
- Files / lines
  - zd_inst_alloc: cfl/src/cfl_zefoz.c:235 (data->h = h;)
  - zefoz_iter: cfl/src/cfl_zefoz.c:433–436 (writes: data->h->coeff[data->zi[i]] = data->B[i];) and calls zhd(...) at 436
  - zhd reads coefficients: cfl/src/cfl_h.c:976 (zhcsrsama(hd_w->hcsr_ma, h->coeff, ...))
- Problem: each thread uses its zd_inst but all zd_inst->h point to the same zh. zefoz_iter writes into h->coeff while zhd (in the same or other threads) reads h->coeff without synchronization → data race, silent wrong eigenvalues/gradients.
- Suggested fix (preferred, minimal-intrusive):
  - Add per-thread coefficient arrays in zd_inst (e.g., add complex double *coeff to zd_inst).
  - Add a new zhd wrapper that accepts an explicit coeff pointer (e.g., zhd_with_coeff(job, w, z, h, coeff, hd_w)) that calls zhcsrsama(hd_w->hcsr_ma, coeff, hd_w->coeff_w) (copy of zhd but using the provided coeff array).
  - In zd_inst_alloc allocate data->coeff = calloc(h->nt, sizeof(complex double)) and initialize from h->coeff if present.
  - In zefoz_iter write to data->coeff[data->zi[i]] = data->B[i]; then call zhd_with_coeff(..., data->coeff, data->hd_w).
  - Free data->coeff in zd_inst_free.
- Rationale: isolates per-thread mutation to per-thread buffers without deep cloning zh, avoids serializing zhd, and keeps most of the API unchanged.
- Test: with OMP_NUM_THREADS > 1, run a representative zefoz grid; compare results vs single-threaded; repeat many times to detect non-determinism.

2) High — d_inst sized to omp_get_num_procs() → possible OOB when OMP_NUM_THREADS > num_procs
- Files / lines
  - zefoz_d_alloc: cfl/src/cfl_zefoz.c:264–266 (ninst = omp_get_num_procs())
  - zefoz_search parallel loop: cfl/src/cfl_zefoz.c:542–545 (tn = omp_get_thread_num(); memcpy(data->d_inst[tn]...))
- Problem: omp_get_num_procs() is not guaranteed to equal the actual thread team size (OMP_NUM_THREADS can exceed it), so tn may index past data->d_inst → crash.
- Suggested fixes:
  - Use omp_get_max_threads() to size data->d_inst (ninst = omp_get_max_threads()), or
  - Add num_threads(ninst) to the parallel pragma to cap the actual team size, or
  - Allocate data->d_inst sized to max(omp_get_num_procs(), omp_get_max_threads()) and/or check tn < ninst at runtime and fallback.
- Test: set OMP_NUM_THREADS to a value larger than available cores and run zefoz_search; previously this can cause OOB; after fix tn accesses should be safe.

3) High — Newton update scaling wrong (factor ≈ 4×)
- Files / lines
  - d2 (perturbative second derivative): cfl/src/cfl_zefoz.c:343–373 (returns Σ creal(mikl * mljk) / (E_k − E_l))
  - C_eval (Jacobian): cfl/src/cfl_zefoz.c:405–413 (data->C = d2(k)-d2(l))
  - inverse + apply: cfl/src/cfl_zefoz.c:442–449 (invert data->C), 456–458 (C^-1 v), 460–462 (update data->B[i] -= 2*data->dwork[i])
- Problem: derivation (PRB 74,195101 convention) gives Hessian J_ij = 2 * Σ Re(⟨k|M_i|l⟩⟨l|M_j|k⟩)/(E_k−E_l) — so d2 returns half the Hessian. The code forms C = d2(k)-d2(l) but then inverts C and applies B -= 2 * (C^-1 v). Algebra shows this is a factor-of-4 in the Newton step (should be B -= 0.5 * C^-1 v if C=d2 difference). This can cause overshoot or divergence.
- Suggested fixes:
  - Easiest: replace the update line with B[i] -= 0.5 * data->dwork[i]; (i.e., apply 0.5 instead of 2) with a comment showing the derivation, or
  - Alternatively (less ambiguous): change C_eval to compute the full Hessian (multiply the d2 result by 2) and keep update as B -= 0.5*C^-1 v or similar, but keep the algebra explicit in comments.
- Test: compare convergence/stability on a case known to converge; check ||v|| reduction per iteration and that Newton reduces residuals faster & reliably after fix.
